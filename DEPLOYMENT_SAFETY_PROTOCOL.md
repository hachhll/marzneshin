## 2. Категорические запреты (Hard Constraints)

1. **ЗАПРЕТ на вторичные туннели (NO WARP, NO Tor):**
   - Никаких Cloudflare WARP, WireGuard outbound или каскадных прокси.
   - Трафик выходит строго и нативно с одного статического немецкого IP `<FRANKFURT_AI_EXIT_IP>`.
   - Исключить скачкообразную смену IP (IP Flapping) между разными провайдерами/ASN во избежание сброса OAuth-сессий Google.

2. **ЗАПРЕТ на использование учетных записей пользователя:**
   - Ни при каких обстоятельствах не использовать логины, пароли, куки, токены или персональные данные пользователя при проверках сервера.
   - Все сетевые проверки выполняются исключительно анонимно на уровне голых протоколов (TCP/TLS handshake, Whois, DNS).

3. **ЗАПРЕТ на сохранение логов и временных файлов:**
   - `access.log` и `error.log` направляются строго в `/dev/null`.
   - Временные файлы после тестов немедленно удаляются, история bash очищается.

4. **ЗАПРЕТ на запросы из РФ:**
   - Все запросы настройки и валидации выполняются только локально на сервере в Германии.

## 3. Детальная защита от дрейфа геопозиции (Google Location Drift RU)

### 3.1. Блокировка доменов телеметрии на сервере (Xray Blackhole)
Сервер уничтожает любые пакеты фоновой телеметрии Android-устройств, чтобы сотовые вышки (MCC 250) и российские BSSID не попали в базы Google:
```json
{
  "type": "field",
  "domain": [
    "location.googleapis.com",
    "connectivitycheck.android.com",
    "connectivitycheck.gstatic.com",
    "domain:gvt1.com",
    "domain:gvt2.com",
    "domain:app-measurement.com",
    "domain:firebase-settings.crashlytics.com"
  ],
  "outboundTag": "block"
}
```

### 3.2. Защита от утечек DNS (DNS Leak Prevention)
1. **Упаковка UDP-DNS:** Клиентские ссылки генерируются строго с `packetEncoding=xudp`. Все DNS-запросы клиентов шифруются и идут внутри защищенного VLESS-туннеля.
2. **Запрет EDNS Client Subnet (ECS):** В конфигурации DNS сервера отключена передача клиентских IP/подсетей провайдерам. Резолв идет строго от имени Франкфурта (`1.1.1.1`, `8.8.8.8`).
3. **Запрет локального DNS:** В клиенте (v2rayNG / NekoBox) режим DNS устанавливается как `Remote DNS only` (только удаленный DNS через туннель).

### 3.3. Регламент действий администратора (Поведение при установке и обслуживании)
1. **Запрет на русские заголовки:** Никаких запросов с сервера с заголовками `Accept-Language: ru`. При системных проверках использовать нейтральный или немецкий язык: `-H "Accept-Language: de-DE,de;q=0.9,en;q=0.8"`.
2. **Запрет на спидтесты в сторону РФ:** Запрещено запускать `speedtest-cli` до серверов в РФ, так как это регистрирует IP в гео-базах Ookla как российский.
3. **Запрет на парсинг и бот-скрипты:** Не запускать автоматизированные циклы запросов к поиску Google или Gemini, которые триггерят reCAPTCHA или дата-центровый антифрод.

### 3.4. Клиентская гигиена (Рекомендации пользователю)
1. **Раздельное туннелирование (Per-App Proxy):** В v2rayNG / NekoBox туннелируются только целевые приложения (Chrome, Gemini, Telegram). Системные службы (*Google Play Services*) исключаются из туннеля, чтобы мобильная телеметрия шла напрямую через сотового оператора, минуя немецкий VPS.
2. **Запрет геолокации в браузере:** В настройках Chrome запретить доступ к местоположению для сайтов Google (`chrome://settings/content/location`).
3. **Защита от утечек WebRTC:** В браузере отключить WebRTC-раскрытие реальных сетевых интерфейсов.

## 4. Пошаговый сценарий ввода нового IP в эксплуатацию

При старте следующей сессии агент действует строго по шагам:

### Шаг 1. Проверка «вслепую» (Zero-Touch Baseline)
1. Проверить доступность SSH на `<FRANKFURT_AI_EXIT_IP>`.
2. Выполнить **ровно один** анонимный системный запрос с сервера:
   ```bash
   curl -s --max-time 5 https://www.youtube.com | grep -o '"INNERTUBE_CONTEXT_GL":"[^"]*"'
   ```
3. Убедиться, что возвращается: `"INNERTUBE_CONTEXT_GL":"DE"`. 
   *(Если вернулось RU — немедленно остановиться и сообщить пользователю).*

### Шаг 2. Обновление конфигурации
1. Внести `<FRANKFURT_AI_EXIT_IP>` в `/opt/vpn/config/vpn.env`.
2. Сгенерировать клиентские ключи VLESS с параметром `packetEncoding=xudp`.
3. Привязать домен `<EXIT_DOMAIN>` к новому IP в DNS.

### Шаг 3. Валидация и самотестирование
1. Выполнить локальный аудит: `/opt/vpn/scripts/self_test.sh` (ожидается 10/10 PASS).
2. Убедиться в отсутствии WireGuard-процессов и открытых лишних портов.
3. Передать пользователю готовую конфигурацию.
